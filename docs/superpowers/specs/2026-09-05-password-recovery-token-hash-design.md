# Password recovery token-hash design

Date: 2026-09-05
Branch: `feat/admin-dashboard-expansion`

## Goal

Replace password recovery's browser-bound PKCE callback dependency with a server-side recovery flow based on Supabase `TokenHash` + `verifyOtp({ type: "recovery" })`.

The user experience requirement is: clicking the recovery email must not consume the recovery credential. The credential is consumed only when the user actually submits a new password. Supabase's own absolute token expiry still applies.

## Current problem

The old flow sent recovery to `/auth/callback?next=/redefinir-senha`, then called `exchangeCodeForSession()`. That required the PKCE verifier stored in the browser that initiated the request. Mobile email apps, custom tabs, a different browser context, overlapping recovery requests, or reused links could therefore fail with `pkce_code_verifier_not_found` or `flow_state_not_found`.

The old `/redefinir-senha` page also required an authenticated customer session, so it could not be reached before the PKCE exchange succeeded.

## Chosen architecture

### 1. Recovery email

The Supabase **Reset Password** email template links to:

```html
<a href="{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=recovery">
  Redefinir senha
</a>
```

Password recovery no longer uses `/auth/callback` as its email destination.

### 2. `GET /auth/confirm`

This route is recovery-specific for this change.

It:

- accepts only `type=recovery`;
- requires a bounded URL-safe `token_hash` value;
- never calls `verifyOtp()` on GET;
- never logs the token hash or full URL;
- stores the token hash in a short-lived `HttpOnly`, `Secure` in production, `SameSite=Lax`, `Path=/` recovery cookie;
- redirects immediately to clean `/redefinir-senha` so the secret leaves the address bar/history surface;
- returns `Cache-Control: private, no-store`.

An email scanner or link preview may hit this GET, but it cannot consume the Supabase token.

### 3. `/redefinir-senha`

The page no longer requires a normal authenticated customer session before rendering.

It renders the password form when either:

- a syntactically valid raw recovery token cookie is present; or
- a Supabase session contains a recent, signed `amr` entry whose method is `recovery`.

A forged raw recovery cookie can at most render the form; the final POST still has to pass Supabase verification. A retry after token consumption cannot be enabled by a custom boolean cookie: it relies on the signed Supabase recovery AMR claim.

If neither context exists, redirect to `/entrar?erro=recovery`.

The page remains `force-dynamic`.

### 4. `POST /api/account/password-recovery`

Keep the existing same-origin check, request-body limit, password validation, and rate limit.

On first submit:

1. Read the recovery token hash from the `HttpOnly` cookie.
2. Call `supabase.auth.verifyOtp({ token_hash, type: "recovery" })` server-side.
3. Apply the Supabase session cookies generated by `verifyOtp()` to the exact response.
4. Clear the raw recovery-token cookie so the one-time token is not retried after it has been consumed.
5. Call `supabase.auth.updateUser({ password })`.
6. If password update succeeds, call `signOut({ scope: "global" })` and return success.

### 5. Retry if password update fails after OTP verification

`verifyOtp()` consumes the one-time token. If OTP verification succeeds but `updateUser()` fails, the response preserves the Supabase session created by `verifyOtp()` while clearing the raw token cookie.

A subsequent submit may skip `verifyOtp()` only when all of these are true:

- the Supabase JWT contains a signed `amr` entry with `method: "recovery"`;
- that recovery AMR timestamp is recent, bounded to 3600 seconds with only a small future-clock skew allowance;
- `supabase.auth.getUser()` validates the session and returns a confirmed user.

This avoids a forgeable custom recovery-marker cookie while still allowing retry after a transient password-update failure. Once password update succeeds, global sign-out ends the recovery session.

## Security constraints

- No open redirect: recovery success destination is fixed.
- `token_hash`, auth codes, access tokens, refresh tokens, cookie values, passwords, and email addresses are never written to recovery diagnostic logs.
- Recovery token cookie is host-only, `HttpOnly`, `SameSite=Lax`, `Path=/`, and `Secure` in production.
- Raw recovery-token cookie lifetime is 3600 seconds and does not bypass Supabase's own token validity.
- Retry authorization is based on Supabase-signed recovery AMR plus server `getUser()` validation, not on a forgeable application marker.
- All auth/recovery route responses use `Cache-Control: private, no-store` where the application controls the response.
- Vercel/proxy caching must not cache responses containing auth `Set-Cookie` headers.
- The existing `/auth/callback` remains for non-recovery auth flows.
- Recovery-specific PKCE diagnostics are removed from the new recovery path.

## Failure behavior

- Missing/malformed `token_hash`: redirect to a safe recovery error.
- Expired/invalid token at final submit: clear the raw recovery cookie and return `Link de recuperação inválido ou expirado.`
- `updateUser()` failure after successful verification: keep the Supabase recovery session so the user can retry without another email, while the raw token remains cleared.
- Retry without a recent signed recovery AMR or without a server-validated user fails closed.
- Global sign-out failure after successful password change reports that the password changed but all sessions could not be closed, matching the existing safety behavior.

## Testing strategy and evidence

TDD is required.

Coverage proves:

1. password-reset request no longer builds a recovery `/auth/callback` redirect;
2. `/auth/confirm` accepts only recovery token-hash input and does not call `verifyOtp()` on GET;
3. `/auth/confirm` sets an HttpOnly recovery cookie, strips the token from the destination, and sends `private, no-store`;
4. `/redefinir-senha` can render from raw-token or recent signed recovery-AMR context without ordinary customer authentication;
5. password-recovery POST calls `verifyOtp({ token_hash, type: "recovery" })` only on final submit;
6. successful verification + password update clears raw recovery context and globally signs out;
7. failed password update after successful verification preserves a retry-capable Supabase recovery session and retry requires recent signed recovery AMR;
8. no recovery credential values are logged.
