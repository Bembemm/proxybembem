# Admin Auth + MFA Design

Date: 2026-08-31
Status: Approved in chat; awaiting written-spec review
Scope: Preview/Sandbox first. No Production rollout and no merge to `main` without explicit owner approval.

## Goal

Replace the current manual Melhor Envio admin-secret gate with a real administrative authentication foundation that can later protect orders, customers, shipping, payments, integrations, and store settings.

The admin area is single-owner. Every new administrative login must require both email/password and a TOTP code generated by an authenticator app on the owner's phone. There is no public admin signup and no MFA bypass.

## Approved security requirements

1. Exactly one authorized admin account.
2. Login uses Supabase Auth email + password.
3. TOTP MFA is mandatory for every new administrative login.
4. No "remember this device" or path that skips MFA.
5. Administrative authorization requires a validated Supabase session at `aal2`.
6. The authorized admin is identified by immutable Supabase user UUID, not merely by email.
7. Only one administrative session may be active at a time.
8. Administrative access expires after 30 minutes of inactivity.
9. The 30-minute inactivity decision is enforced server-side, not by a browser timer or editable client cookie.
10. A new successful admin login revokes any previous admin session.
11. SMS is not an MFA fallback.
12. There is no self-service "skip 2FA" recovery path. If the owner loses the authenticator device, recovery is performed manually through Supabase administration and a new TOTP factor is enrolled.
13. If the application cannot verify admin authorization, it fails closed.
14. The existing Melhor Envio OAuth callback stays public because the provider must call it, but it remains protected by the existing short-lived, one-time OAuth `state` flow.

## Chosen approach

Use the official Supabase Auth client stack for Next.js SSR:

- `@supabase/supabase-js`
- `@supabase/ssr`
- cookie-backed Supabase Auth session
- Next.js `proxy.ts` for auth-token refresh and protected-route handling
- server-side `getClaims()` validation for trusted JWT claims
- TOTP enrollment/challenge/verification through Supabase MFA APIs
- a small server-owned `admin_sessions` table for strict inactivity and single-session enforcement

This is preferred over browser-only timeout logic or layering MFA on top of the existing shared admin secret.

## Authentication flow

### First setup

1. The sole admin user is created manually in Supabase Auth. Public signup is disabled/not exposed.
2. The admin opens `/admin/login` and enters email + password.
3. The server validates the Supabase user and verifies that `sub` equals the configured authorized admin UUID.
4. If no verified TOTP factor exists, the admin is sent to `/admin/setup-mfa`.
5. Supabase creates a TOTP enrollment secret and QR code.
6. The owner scans the QR code using an authenticator app on the phone and enters the first code.
7. The application challenges and verifies the factor.
8. Only after the session reaches `aal2` may an administrative session be activated.

### Normal login

1. `/admin/login` accepts email + password.
2. A successful password login is only `aal1` and does not grant access to protected admin content.
3. The user is sent to `/admin/mfa`.
4. The user enters the current 6-digit TOTP code from the authenticator app.
5. After successful verification, the Supabase session reaches `aal2`.
6. The server verifies the admin UUID and activates a new administrative session.
7. Any previous administrative session is revoked.
8. The user is redirected to `/admin` or the originally requested admin destination.

## Admin authorization model

A shared server helper will be the single authorization boundary for admin pages and administrative APIs. Conceptually it will perform:

1. Validate Supabase JWT claims server-side using `getClaims()`.
2. Require a non-anonymous authenticated user.
3. Require `sub` to equal the configured single admin UUID.
4. Require `aal === "aal2"`.
5. Require a valid `session_id` claim.
6. Look up the matching active server-side admin session.
7. Reject revoked or missing sessions.
8. Reject sessions whose `last_activity_at` is 30 minutes or more in the past.
9. Optionally update `last_activity_at` for interactive admin activity.

No client-provided role, email, timer, or local-storage value is sufficient to authorize an admin request.

## Server-side inactivity control

Supabase's normal Auth session remains the identity layer. The application adds a separate administrative-session layer so the 30-minute rule is exact enough for this admin use case and does not depend on plan-specific Supabase session-timeout features.

Recommended database shape:

- `id uuid primary key`
- `auth_session_id uuid not null unique`
- `user_id uuid not null`
- `created_at timestamptz not null`
- `last_activity_at timestamptz not null`
- `revoked_at timestamptz null`

The table is server-owned. `anon` and normal `authenticated` browser access must not be able to read or mutate it directly.

### Activity semantics

Interactive protected admin requests may refresh `last_activity_at`. Background polling, passive refreshes, or merely leaving a tab open must not keep the administrative session alive.

The central auth helper therefore supports two modes:

- authorization check without activity refresh
- authorization check with activity refresh

Future background order polling must use the non-refreshing mode.

### Timeout behavior

When an admin request finds 30 minutes or more of inactivity:

1. The admin-session row is treated as expired/revoked.
2. The Supabase browser session is signed out/cleared for the admin flow so an existing `aal2` token cannot silently skip the requested re-login experience.
3. The user is redirected to `/admin/login`.
4. Re-entry requires email + password + a new TOTP verification.

## Single-session behavior

When a new `aal2` admin login is activated, all previously active admin-session rows for the owner are revoked before/while activating the new one in an atomic server-side operation.

Result:

- logging in on a second browser/device invalidates the first administrative session;
- the previous browser loses admin access on its next protected request;
- every new login still requires password + TOTP.

This rule is enforced by the application's admin-session layer rather than relying on a plan-specific Supabase single-session feature.

## Route structure

Initial routes/pages:

- `/admin/login` — email/password login
- `/admin/setup-mfa` — one-time TOTP enrollment for the authorized admin when no verified factor exists
- `/admin/mfa` — TOTP challenge after password login
- `/admin` — protected admin landing page/foundation
- `/admin/integrations/melhor-envio` — existing integration page, now protected by admin auth
- logout action/route — revokes the admin session and signs out of Supabase

Protected admin APIs, including Melhor Envio administrative actions, must call the same server authorization helper instead of trusting only page-level protection.

## Melhor Envio integration change

Current behavior:

`/admin/integrations/melhor-envio` asks for `adminSecret`, and `/api/internal/melhor-envio/oauth/start` compares it against `MELHOR_ENVIO_OAUTH_ADMIN_SECRET`.

Target behavior:

1. The admin page is accessible only to the authorized `aal2` admin session.
2. The visible "Segredo administrativo" field is removed.
3. `/api/internal/melhor-envio/oauth/start` requires the same valid admin session and retains same-origin/rate-limit protections.
4. The existing OAuth `state` generation, SHA-256 storage, expiry, one-shot consumption, token encryption, and provider callback behavior are preserved.
5. The provider callback remains public and must not require the browser's admin session because Melhor Envio calls it directly.

After this transition is validated, `MELHOR_ENVIO_OAUTH_ADMIN_SECRET` can be removed from the runtime contract if no remaining route depends on it.

## Environment/configuration

New browser-safe Supabase Auth configuration is expected to use the current Supabase project URL plus a Supabase publishable key, following the official SSR pattern.

Expected new names:

- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`
- `ADMIN_USER_ID` — server-only immutable UUID allowlist for the sole admin

Existing privileged `SUPABASE_SECRET_KEY` remains server-only and must never be exposed to browser code.

No secret values are committed to the repository.

## Account provisioning and recovery

- No public admin signup UI.
- The sole admin account is provisioned manually.
- The authorized UUID is captured in server configuration only after the account exists.
- TOTP enrollment is performed immediately during initial setup.
- No SMS fallback.
- No email-based MFA bypass.
- No "trusted device" bypass.
- No self-service factor reset in the initial admin UI.
- If the phone is lost, the owner uses Supabase administrative access to remove/reset the old TOTP factor and enroll a new one.

A password-reset feature is not required for this initial scope; it can be added later if needed without weakening the mandatory TOTP gate.

## Error and failure behavior

- Wrong password: no session activation; generic login error.
- Correct password but no TOTP verification: admin remains blocked at `aal1`.
- Wrong/expired TOTP: admin remains blocked.
- Authenticated non-owner UUID: denied.
- Missing/invalid claims: denied.
- Missing `aal2`: denied or redirected to MFA flow as appropriate.
- Missing/revoked/expired admin-session row: denied; timeout path forces a fresh login.
- Database/auth verification failure: fail closed.
- Old browser after a newer login: denied on next protected request.
- Administrative API without valid admin session: 401/403 as appropriate.
- Logout: revoke admin-session row and sign out of Supabase.

Authentication routes and protected admin responses must not be publicly cached.

## Security boundaries

- Authorization decisions are server-side.
- `getSession()` data is not trusted by itself for server authorization.
- Supabase secret/service credentials remain server-only.
- The publishable key may be present in browser code as designed by Supabase; it grants no admin privilege by itself.
- Admin tables and future customer/order data must be protected independently from the UI. Hiding buttons is never treated as authorization.
- Sensitive POST routes retain same-origin/CSRF defenses where applicable.
- Existing checkout, payment webhook, shipping quote, Cron, and public customer flows remain independent from admin login.

## Future admin expansion

This work builds the security foundation only. It does not yet build the full store dashboard.

Future sections can reuse the same authorization boundary for:

- orders and order status
- payment status
- customer and shipping details
- production workflow
- shipping labels/tracking
- Mercado Pago integration status
- Melhor Envio integration management
- products/prices
- store configuration

No second authentication system should be introduced for these features.

## Testing strategy

### Automated

Cover at least:

- admin UUID allowlist accepts only the configured UUID;
- `aal1` is rejected for protected admin access;
- `aal2` is required;
- missing/invalid `session_id` is rejected;
- active admin session succeeds;
- 30-minute boundary expires correctly;
- interactive requests refresh activity;
- non-interactive/background checks do not refresh activity;
- new session atomically revokes the previous session;
- revoked session is rejected;
- failure to read authorization state fails closed;
- Melhor Envio OAuth start rejects unauthenticated/`aal1` requests;
- existing OAuth state behavior remains intact.

Run repository verification gates after implementation:

- `pnpm test`
- `pnpm typecheck`
- `pnpm build`

### Preview/Sandbox acceptance

Before Production:

1. Create/provision the sole Preview/Sandbox admin account.
2. Log in with password.
3. Enroll TOTP through QR code.
4. Confirm the first code and reach `aal2`.
5. Verify `/admin` and Melhor Envio integration page work.
6. Verify password-only (`aal1`) cannot reach admin content.
7. Verify an invalid TOTP cannot reach admin content.
8. Verify logout blocks further admin access.
9. Verify 30 minutes of inactivity requires a completely fresh password + TOTP login.
10. Verify a login in a second browser/device revokes the first admin session.
11. Verify Melhor Envio reauthorization still completes successfully through its existing OAuth callback/state protection.
12. Review runtime logs for auth/session errors without logging secrets or auth cookies.

## Rollout constraints

- Implement and validate on the existing feature branch/Preview first.
- Do not switch Mercado Pago or Melhor Envio to Production as part of this auth feature.
- Do not merge to `main` without explicit owner approval.
- Keep the future KingHost migration in mind: the admin-session schema and authorization boundary should remain ordinary Postgres/application concepts where practical, while Supabase Auth-specific code stays isolated behind auth helpers so it can be replaced during migration.

## Out of scope

- Full orders dashboard
- customer-management UI
- analytics/graphs
- product management
- multiple admins or role hierarchy
- public signup
- SMS MFA
- trusted-device bypass
- self-service MFA recovery
- Production provider rollout
- KingHost migration
